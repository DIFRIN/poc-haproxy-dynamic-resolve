# Failure injection

How each failure is injected, what command does it, and what the architecture is required
to do in response. The expected behaviour below comes from the brief's non-negotiable
rules; the **observed** behaviour for each is recorded in
[../final-validation.md](../final-validation.md) and
[../benchmark-report.md](../benchmark-report.md).

---

## Method

Failures are injected with ordinary Docker operations against the running stack, with no
modification to the components under test. That matters: a failure injected by rewriting a
config tests the rewrite, not the architecture.

| Injection | Command | Models |
|---|---|---|
| Process/service down | `docker stop <container>` | service crash or host loss for that role |
| Hard node loss | `docker kill <container>` | power loss / kernel panic, no graceful shutdown |
| Node unreachable but alive | `docker pause <container>` | network partition or a hung process |

`docker kill` is used for the hard-failover case specifically because it gives no
opportunity for a graceful VRRP withdraw — the peer must detect the loss by timeout, which
is the pessimistic case and the one worth measuring.

Every failover run records:

- VIP owner before and after (`ip addr show eth0` in each node)
- Time from injection to VIP movement — taken from the `[vrrp]` lines the notify hook
  writes with millisecond timestamps, not from a polling loop, so the figure is not
  quantised by the poll interval
- Whether client traffic actually resumed, and any observed outage window
- The relevant node's health check output at the moment of the fault

## 1. PowerDNS failure — the VIP must NOT move

```
        Active HAProxy  (stays active)
              |
          local dnsdist
          /           \
     PDNS 1 X        PDNS 2 OK
```

```bash
docker stop poc-pdns-1        # then mirror with poc-pdns-2
```

**Required behaviour.** dnsdist detects the failure via its 1 s health probes, marks the
backend down, and serves everything from the surviving server. The VIP **does not move**.

**Why this is the rule.** A PowerDNS outage is not a proxy-node failure. Moving the VIP
would move the problem onto a node whose dnsdist has exactly the same two backends and is
in exactly the same condition — it would add an outage window on top of an outage without
restoring anything.

**What is asserted.** Names still resolve through both dnsdist instances; the VIP owner is
unchanged; the health check on the active node still exits 0.

**Restore.** `docker start poc-pdns-1`, then confirm dnsdist reintroduces the backend and
round-robin distribution returns to including it. dnsdist does this automatically; the
`rise` setting controls how many consecutive successes are required.

## 2. dnsdist failure — the VIP MUST move (TARGET only)

```
Active HAProxy
      |
local dnsdist X      <- this node can no longer resolve anything
      |
health check fails
      |
VIP moves
      |
other HAProxy + its own local dnsdist
```

```bash
# identify the active node, then stop the dnsdist local to it
docker stop poc-dnsdist-<n>
```

**Required behaviour.** The active node's health check fails (it cannot get a DNS answer
from its local dnsdist), its effective VRRP priority drops below its peer's, and the VIP
moves. Traffic resumes through the other node's local dnsdist, which has its own
independent view of both PowerDNS servers.

**The subtlety this tests.** The health check must fail on *silence*, not on a bad DNS
answer. `dig` exits 0 whenever it receives a response of any kind, including SERVFAIL, and
non-zero only when nothing comes back. That is exactly the required discrimination — see
scenario 3.

**Restore.** `docker start poc-dnsdist-<n>`. The node becomes eligible again and, because
its priority is higher, preempts the VIP back.

## 3. DNS response errors — the VIP must NOT move

```
NXDOMAIN / SERVFAIL   ->  a DNS RESULT       ->  VIP stays
no response / timeout ->  INFRASTRUCTURE     ->  VIP may move
```

```bash
# The client lives in an overlay, not a profile -- apply it with a second -f.
# DNS answers on 53 (DNS_PORT in .env); 172.28.0.31 is dnsdist-1.
# SERVFAIL, produced by real PowerDNS: a zone row with no SOA record
docker compose -f compose.yaml -f compose.bench.yaml run --rm client \
    -mode=dnstest -server=172.28.0.31:53 -name=servfail.test.domain
# NXDOMAIN, produced by real PowerDNS: an undefined name inside a served zone
docker compose -f compose.yaml -f compose.bench.yaml run --rm client \
    -mode=dnstest -server=172.28.0.31:53 -name=nx.test.domain
```

Both are generated by PowerDNS itself, not spoofed or simulated client-side — a synthetic
NXDOMAIN would not exercise the same code path and would prove nothing.

**Required behaviour.** Neither moves the VIP. Both are answers; the infrastructure that
produced them is working correctly.

**What is asserted.** The VIP owner is unchanged across a burst of both, and the active
node's health check still exits 0.

## 4. Active HAProxy failure — the VIP MUST move

```
Active HAProxy X
      |
Keepalived detects failure (advert timeout)
      |
VIP moves to the standby
      |
standby becomes ACTIVE and takes client traffic
```

```bash
# hard loss, no graceful VRRP withdraw -- the pessimistic case
docker kill poc-haproxy-<active>
```

**Required behaviour.** After the master-down interval (`3 × advert_int + skew`, so
~3.6 s at `advert_int 1`) the standby takes the VIP via gratuitous ARP and client traffic
resumes.

**Downstream layer is unaffected.** In CURRENT the new active node uses the same two
Squids. In TARGET it uses its own local dnsdist. Neither architecture requires the
downstream layer to move.

**Restore.** `docker start poc-haproxy-<n>`. It returns as BACKUP, then preempts the VIP
back once its priority (150) exceeds the current holder's (100) — assuming its own health
check passes.

## 5. Degraded node — health-check-driven failover

Rather than killing a node outright, this covers the case where the node is **alive but
unable to serve**: its proxy stack is unhealthy even though the process is running.

```bash
# make the active node's health check fail without stopping any container
docker exec poc-haproxy-<active> sh -c 'mv /run/keepalived/check.sh /run/keepalived/check.sh.bak'
# ... then restore it
```

**Required behaviour.** Because the check is weighted (`weight -60`), the active node's
effective priority falls from 150 to 90, below the standby's 100. A real election follows
and the VIP moves. Preemption returns it once the check passes again.

This is the mechanism that makes scenario 2 work; testing it directly isolates the
weighting from the DNS behaviour.

## Not covered

Stated here so the gap is explicit rather than implied by omission:

- **Combined and cascading failures** — e.g. PowerDNS 1 down *and* the active dnsdist
  failing simultaneously. Single-fault scenarios only.
- **Network-level faults** — packet loss, added latency, MTU problems, asymmetric
  partitions. All faults here are process- or container-level.
- **Host failure** — both HAProxy nodes share one physical host in this POC, so a
  host-level fault is not survivable and cannot be meaningfully tested here.
- **Split-brain** — with two nodes and no fencing device, a partition that isolates both
  nodes from each other while both remain healthy is not exercised. Production would need
  a fencing or quorum strategy, and this POC does not evaluate one.
- **Recovery under sustained load** — failover was measured with traffic running, but not
  with a full 10,000-tunnel population held open across the event.
